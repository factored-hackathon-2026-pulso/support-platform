# Database: Postgres, migrations and roles

What the support platform needs from the shared Postgres, and how its schema gets there. Infra
creates the database and the roles from this page; the platform never creates roles. The full
environment contract (every `CC_*` variable) is in [`../deploy-env.md`](../deploy-env.md); this
page owns the database part.

## 1. Engines

| Where | Engine | `CC_DATABASE_URL` |
|---|---|---|
| Production, shared environment, compose | Postgres 13 or newer (tested on 16) | `postgresql://<role>:<password>@<host>:5432/<database>` |
| Local development (default) | SQLite file `backend/cc_platform.db` | unset, or `sqlite+aiosqlite:///<absolute path>` |
| Unit tests | SQLite, or Postgres with `CC_TEST_DATABASE_URL` (section 7) | set by the tests |

- Driver: **psycopg 3** (async, `psycopg[binary]`). `postgres://` and `postgresql://` URLs are
  read as `postgresql+psycopg://`; writing the driver yourself is fine too.
- The URL is a secret (it holds the password): inject it, never log it. The platform only logs it
  with the password masked (`postgresql+psycopg://app:***@host/db`).
- TLS: add libpq parameters to the URL, e.g. `?sslmode=require` (or `verify-full` with
  `sslrootcert=<path>`).
- Encoding UTF-8 (Spanish and Portuguese text). Any collation works; nothing relies on it.

## 2. Migrations

The schema is a chain of Alembic revisions in
`backend/src/cc_platform/infrastructure/persistence/sqlalchemy/migrations/versions/`:

| Revision | What |
|---|---|
| `0001_baseline` | The schema as of slice 22 (28 tables). On Postgres also the `event_log` append-only triggers (section 4). |
| `0002_suggestion_truncated` | `copilot_suggestions.truncated` (PR 25) |
| `0003_engine_announce` | `notifications.proposal_id/agent_id/improvement`; drops the `builder_proposals.registered_by` foreign key, so it may be `engine` (PR 17, ADR 0007) |
| `0004_engine_release` | `assistant_sessions.agent_release`, `copilot_suggestions.release` (PR 27) |

How they run:

- **On start (default).** `cc-api` (and any `uvicorn … create_app --factory`) applies the pending
  revisions before serving (`CC_MIGRATE_ON_START=true`). Several processes may start at once.
- **As a one-shot job.** `cc-migrate` (same image, same `CC_DATABASE_URL`; it reads no other
  secret) applies them and exits `0`. Then run `cc-api` with `CC_MIGRATE_ON_START=false`: it
  only checks that the database is at the head revision and refuses to start otherwise
  (`SchemaNotMigratedError: … run cc-migrate`). This is the way to keep DDL rights away from the
  serving role (section 3).
- `cc-migrate check` exits `1` unless the database is at head (changes nothing; usable as a
  readiness or pre-deploy check); `cc-migrate current` prints the current and head revisions.

Guarantees:

- **Idempotent.** At head, `cc-migrate` (or a start) changes nothing.
- **No race.** On Postgres the whole upgrade is one transaction that first takes
  `pg_advisory_xact_lock(3580844065961881786)` (a constant key); a second process waits for it
  and then finds the head. On a SQLite file the lock is an exclusive `flock` on
  `<database file>-migrate.lock` next to it. Tested with three processes started together.
- **Transactional on Postgres.** A failed revision rolls everything back, including the
  version stamp. (SQLite has no transactional DDL: a failed local upgrade may leave a partial
  change; it is a development database.)
- **Forward-only.** Revisions have no downgrade. To undo a change, ship a new revision; to undo a
  bad deploy, restore the backup taken before it.
- **Pre-migration SQLite files are adopted.** A database created before Alembic (`create_all`
  at startup, slice 22 to PR 28) has no `alembic_version`: it is stamped with the newest of the
  four revisions above whose tables and columns it has, then upgraded. A file older than slice
  22 cannot be adopted: the start fails with `OutdatedSchemaError` naming what is missing (move
  that development file aside; the seed recreates the sample data). There is no copy from
  SQLite to Postgres: production starts on an empty Postgres.

For developers, a schema change is: edit `tables.py`, run
`uv run cc-migrate revision -m "what changed"` (writes the next revision, autogenerated against
a scratch database at head), review it (frozen types as in `0001_baseline`, a `server_default`
for a new `NOT NULL` column, `op.batch_alter_table` so SQLite can apply it) and run the tests:
`tests/unit/infrastructure/test_migrations.py` fails while `tables.py` and the head differ.
Nobody deletes a database any more.

## 3. Roles and grants

Three roles. Names are suggestions; the grants are what matters. All objects live in the
`public` schema of the platform's own database (e.g. `cc_platform`).

### 3.1 `cc_platform_owner`: owns the schema, runs the migrations

```sql
CREATE ROLE cc_platform_owner LOGIN PASSWORD '<secret>';
CREATE DATABASE cc_platform OWNER cc_platform_owner ENCODING 'UTF8';
\connect cc_platform
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT ALL ON SCHEMA public TO cc_platform_owner;
```

It creates the tables, indexes, the `event_log_reject_change()` function and its triggers, and
the `alembic_version` table. Used by `cc-migrate` (or by `cc-api` when one role does it all,
below).

### 3.2 `cc_platform_app`: the running API (read/write)

```sql
CREATE ROLE cc_platform_app LOGIN PASSWORD '<secret>';
GRANT CONNECT ON DATABASE cc_platform TO cc_platform_app;
GRANT USAGE ON SCHEMA public TO cc_platform_app;

-- Tables the migrations create later get the same rights automatically.
ALTER DEFAULT PRIVILEGES FOR ROLE cc_platform_owner IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO cc_platform_app;
ALTER DEFAULT PRIVILEGES FOR ROLE cc_platform_owner IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO cc_platform_app;
```

After `cc-migrate` has run (re-run after every deploy that adds tables; every statement is
idempotent):

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO cc_platform_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO cc_platform_app;
-- event_log is append-only (section 4): read and append, nothing else.
REVOKE UPDATE, DELETE, TRUNCATE ON event_log FROM cc_platform_app;
-- The schema version is the migration job's business.
REVOKE INSERT, UPDATE, DELETE ON alembic_version FROM cc_platform_app;
```

What the app does with them, by table:

| Tables | Rights | Why |
|---|---|---|
| `event_log` | `SELECT`, `INSERT` (+ `USAGE` on `event_log_sequence_seq`) | the audit and the history; append-only |
| `turns`, `assignments` | `SELECT`, `INSERT` (UPDATE/DELETE unused, harmless) | append-only by design |
| `notifications` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | read marks; only the newest 200 per person are kept |
| `copilot_suggestions` | `SELECT`, `INSERT`, `UPDATE` | the 24 h purge clears the texts (an UPDATE) |
| `dev_mailbox` | `SELECT`, `INSERT` | development only; empty in production |
| every other table (`staff`, `teams`, `admin_roster`, `platform_settings`, `login_accounts`, `invitations`, `password_resets`, `mfa_challenges`, `staff_sessions`, `analyst_availability`, `staff_preferences`, `customers`, `cases`, `escalations`, `calls`, `customer_case_slots`, `assistant_sessions`, `copilot_threads`, `case_type_maturity`, `builder_threads`, `builder_proposals`, `bank_customer_links`) | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | aggregates saved with optimistic locking |
| `alembic_version` | `SELECT` | the start-up check (`CC_MIGRATE_ON_START=false`) |

The internal evidence route (`GET /api/v1/internal/evidence/cases`, PR 27) runs inside the
platform with this role: it reads `cases` (`id`, `case_type`, `channel`, `language`,
`priority`, `close_reason`, `opened_at`). It needs nothing from the exporter's role.

**Simpler setup (one role).** If infra prefers a single platform role, make it the owner
(`cc_platform_owner` with `LOGIN`), keep `CC_MIGRATE_ON_START=true` and skip 3.2. The
`event_log` triggers still hold (only a deliberate `DROP TRIGGER` by the owner would bypass them).

### 3.3 `platform_exporter`: the engine's read-only role

The improvement engine's `platform-exporter` reads, never writes. Column-level grants, so the
database itself refuses free text and personal data (the exporter's own allow-list is the
engine's; these are the columns of that list that exist here, plus `cases.case_type`):

```sql
CREATE ROLE platform_exporter LOGIN PASSWORD '<secret>';
ALTER ROLE platform_exporter SET default_transaction_read_only = on;
GRANT CONNECT ON DATABASE cc_platform TO platform_exporter;
GRANT USAGE ON SCHEMA public TO platform_exporter;

GRANT SELECT (sequence, event_id, event_type, entity, entity_id, case_id, actor_role,
              actor_id, event_time, ingested_at, payload) ON event_log TO platform_exporter;
GRANT SELECT (id, customer_id, channel, language, priority, case_type, opened_at, sla_due_at,
              previous_case_id, rating_score, rated_at) ON cases TO platform_exporter;
GRANT SELECT (id, simulator) ON customers TO platform_exporter;
GRANT SELECT (id, roles, languages, team_id, active) ON staff TO platform_exporter;
GRANT SELECT (id, case_id, sequence, kind, audience, author_role, created_at)
    ON turns TO platform_exporter;
GRANT SELECT (id, case_id, staff_id, reason, policy_rule_id, strategy,
              open_cases_at_assignment, waited_seconds, previous_staff_id, paused_override,
              assigned_at) ON assignments TO platform_exporter;
GRANT SELECT (customer_id, open_case_id) ON customer_case_slots TO platform_exporter;
```

- The brief's minimum is the first two (`event_log`, `cases` with `case_type`); the other five
  are on the exporter's current allow-list. Grant only the tables it really reads.
- Not granted on purpose: `cases.status`, `closed_at`, `close_reason`, previews, notes and
  comments (mutable state or free text, also outside the exporter's list), every other table.
- The allow-list names `tenant_id` (`event_log`, `cases`) and `staff.team`: those columns do
  not exist in the platform; the exporter must not select them.
- Column grants follow new columns only when added here: a revision that adds a column the
  exporter needs comes with a line for this section.

## 4. `event_log` is append-only

- Postgres: revision `0001_baseline` installs `event_log_reject_change()` and two triggers,
  `event_log_append_only` (`BEFORE UPDATE OR DELETE … FOR EACH ROW`) and
  `event_log_no_truncate` (`BEFORE TRUNCATE`). Any of those statements fails with
  `event_log is append-only: <op> is not allowed`, whoever runs it. The app role also lacks the
  rights (section 3.2). Test: `test_event_log_is_append_only_on_postgres`.
- SQLite (development): as before, the guarantee is the code (no repository updates or deletes
  an `event_log` row).
- `event_log.sequence` is a `bigint` identity on Postgres (`event_log_sequence_seq`): the
  exporter's cursor.

## 5. Connections and pool

Per API process (one uvicorn worker is the supported setup):

| Setting | Default | What |
|---|---|---|
| `CC_DATABASE_POOL_SIZE` | `5` | connections kept open |
| `CC_DATABASE_MAX_OVERFLOW` | `5` | extra connections under load (so at most 10 per process) |
| `CC_DATABASE_POOL_TIMEOUT_SECONDS` | `10` | wait for a free connection before the request fails |
| fixed | 1800 s | connections are recycled after 30 minutes |
| fixed | on | `pool_pre_ping`: a dropped connection is replaced, not handed out |
| fixed | 5 s | `connect_timeout` |
| fixed | `cc-platform` | `application_name` (visible in `pg_stat_activity`) |

Budget for the shared server: `(POOL_SIZE + MAX_OVERFLOW) × processes` for `cc_platform_app`,
plus 2 for `cc-migrate`. With the defaults and one process: 10 (+2). Suggested role limits:
`ALTER ROLE cc_platform_app CONNECTION LIMIT 20;` and, as a guard against stuck transactions,
`ALTER ROLE cc_platform_app SET idle_in_transaction_session_timeout = '60s';`. Do not set a
`statement_timeout` on the owner role shorter than a migration may take.

Transactions use Postgres' default `READ COMMITTED`. Concurrent writes are guarded by a
`version` column (compare-and-set); a lost race, a serialization failure, a deadlock or a lock
timeout (`40001`, `40P01`, `55P03`) is retried by the command or answered `409
concurrent_update`.

## 6. Readiness and backups

- Healthy database for the platform = reachable **and** at the head revision
  (`cc-migrate check`, or `current_revision()` in code). `GET /readyz` (runtime contract) uses
  that definition.
- Back up before each deploy that brings a new revision (`cc-migrate current` shows whether it
  does); migrations are forward-only.

## 7. Running the backend tests on Postgres

```bash
cd backend
scripts/test-postgres.sh            # starts a throwaway postgres:16-alpine (docker or podman),
                                    # runs the whole suite on it, removes the container
scripts/test-postgres.sh -k migrations -q   # any pytest arguments
```

Or against a server you already have (an admin connection; the tests create and drop their own
databases, named `cc_test_<pid>_…`):

```bash
CC_TEST_DATABASE_URL=postgresql://postgres:<password>@127.0.0.1:<port>/postgres uv run pytest
```

With the variable set, each SQLite URL a test opens becomes a fresh Postgres database cloned from
a template migrated once per session; tests marked `sqlite_only` (pre-Alembic SQLite files, SQLite
lock errors) are skipped and tests marked `postgres_only` (the `event_log` triggers) run.
